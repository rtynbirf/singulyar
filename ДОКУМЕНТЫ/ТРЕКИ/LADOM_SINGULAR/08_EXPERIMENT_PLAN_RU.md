# План экспериментов: как превратить реконструкцию в проверяемую модель

## Цель
Проверить, насколько layout-first workflow улучшает композиционный контроль по сравнению с prompt-only baseline, не выдавая чужие результаты за воспроизведённые.

## Набор задач
Создать минимум 100 тестовых сцен, разделённых по типам:
- 20 сцен с 2–4 объектами и заданными позициями;
- 20 сцен с отношениями (слева/справа/за/внутри/частично перекрывает);
- 15 сцен с точным количеством объектов;
- 15 сцен с текстом/плакатом/табличкой на нескольких языках;
- 10 сцен с 2–4 референсами и заданными ролями;
- 10 задач локального редактирования одного элемента;
- 10 adversarial-сцен: похожие объекты, длинные инструкции, конфликтующие условия, пустые/неполные layout.

Для каждой задачи хранить prompt, gold-layout, референсы, требования, запрещённые изменения, модель/версию, seed (если доступен), параметры, API request id, стоимость и результат.

## A/B протокол
A: обычная генерация по текстовому запросу.  
B: сначала создание/ручная коррекция layout, затем render.  
Одинаковая модель/версия, сопоставимые настройки и одинаковый бюджет попыток. Если API не даёт фиксировать seed, отметить это как ограничение и повторить каждую задачу минимум 3 раза.

## Метрики и критерии
- Объекты: entity recall ≥ 0.90 на простом наборе; считать отдельно по типам сцен.
- Количество: exact count ≥ 0.90 на сценах с явным количеством.
- Пространство: медианная ошибка центра ≤ 0.08 диагонали кадра; отдельно сообщать IoU bbox, если есть детектор/сегментация.
- Текст: exact OCR match; сообщать отдельно по языку, размеру и фону.
- Локальность правки: измерять perceptual difference внутри целевой маски и вне неё; вне маски — чем меньше изменение, тем лучше, но не считать это доказательством без визуального обзора.
- Слепое предпочтение: минимум два оценщика на выборке, скрыть метод и имя модели.
- Стоимость: доллары/кредиты на успешный результат; считать все попытки, включая отклонённые и неудачные, если они оплачиваются.

Пороговые значения выше — стартовые acceptance criteria нашего эксперимента, не опубликованные показатели Reve. Их следует уточнить после пилота.

## Обязательные контрольные тесты
1. Перемещение одного объекта не должно менять bbox закреплённых объектов в layout.
2. `remove` действительно удаляет сущность из следующего layout, а не только скрывает её в UI.
3. `keep`/аналогичный lock должен быть проверен на уровне API-схемы; не придумывать неподдерживаемое поле.
4. Изменение текста проверять OCR-ом и человеком.
5. Проверять нормализованные bbox на выход за границы и нулевые/отрицательные размеры.
6. Сравнивать исходный и итоговый layout diff-ом до рендера.
7. При ошибке API сохранять входы и не терять последнюю валидную версию layout.
8. Не отправлять секрет API в браузер; прокси должен иметь auth/rate limit/лимит бюджета.
9. Отвергнутый контент и повторные вызовы учитывать в бюджете и журнале.
10. Случайно перемешать A/B результаты для слепой оценки.

## Итоговый вердикт
Layout-first считается полезным не по красоте одного примера, а если улучшает count accuracy, spatial adherence и edit locality на заранее зафиксированном наборе задач при приемлемой стоимости/задержке. Если улучшение есть только в субъективном предпочтении, это следует указывать отдельно.
