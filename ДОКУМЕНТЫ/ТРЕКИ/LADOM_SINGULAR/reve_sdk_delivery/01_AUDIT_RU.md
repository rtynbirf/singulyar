# Инженерный аудит Reve SDK

## 1. Итог
Reve SDK следует рассматривать как интерфейс к удалённой системе генерации/редактирования изображений, а не как исходный код самой модели. Практически значимая особенность v2 — композиционный workflow с Layout: описать регионы изображения, рендерить по ним результат и извлекать layout обратно для дальнейшей работы.

## 2. Что подтверждается открытым репозиторием

### Python SDK, API v1
Публичные операции, перечисленные в README: `create`, `remix`, `edit`, `get_balance`, `list_effects`; также перечислены операции постобработки вроде `upscale`, `remove_background`, `fit_image`, `effect`. Конкретные аргументы и совместимость нужно проверять по установленной версии пакета и сигнатурам исходника перед выпуском.

### Python SDK, API v2 / Layout
README описывает `create`, `extract_layout`, `create_layout`, `render_layout`, `reconcile_layout`. Layout — структурированное описание регионов; регион содержит, в частности, label, prompt и bounding box. Координаты описываются как нормализованные. Пример `v2_layout_pipeline.py` показывает последовательность: создать layout → изменить его командой → отрендерить → извлечь layout из результата.

### Операции изменения композиции
Skill-документация показывает команды, в том числе `add`, `shift`, `remove`, `place`, `keep`, `change`, и рекомендует `reconcile_layout` после непосредственного редактирования layout. Это публичный workflow; он не доказывает, что модель внутри использует строго определённый алгоритм пространственного внимания или конкретную внутреннюю архитектуру.

### Web SDK и визуальный пример
Web SDK описан как лёгкая обёртка над `fetch`, без обязательных runtime-зависимостей; в README также упомянут компонент наложения рамок layout. Пример nodes — демонстрационное приложение на Next.js/React Flow с узлами создания/извлечения/рендеринга layout и редактирования изображений. Документация примера сама отмечает ограничения демонстрационного уровня (например, отсутствие полноценной авторизации и сборки мусора хранилища).

### Ответы API и ошибки
README упоминает поля ответа наподобие `request_id`, `credits_used`, `credits_remaining`, `version`, `content_violation`. В клиенте следует обрабатывать не только HTTP-статус: возможен ответ без изображения при content violation. Формат полей и точное поведение следует сверять с версией API, реально используемой приложением.

## 3. Что не подтверждено / UNKNOWN
- Полная архитектура модели, веса и число параметров.
- Обучающие данные, их происхождение и лицензирование в деталях.
- Функция потерь, оптимизатор, расписание обучения и гиперпараметры.
- Точный внутренний алгоритм семплирования/денойзинга.
- Внутреннее устройство контроля композиции, attention maps, региональных масок и механизмов приоритизации prompt.
- Гарантии детерминизма, точной воспроизводимости или фиксированного числа шагов генерации, если это прямо не обещано контрактом API.
- Совместимость каждого примера с текущей production-версией сервиса без запуска интеграционных тестов.

Нельзя выдавать реконструкцию этих внутренних механизмов за факт. Исследовательская гипотеза допустима только с явной маркировкой `HYPOTHESIS` и проверяемым экспериментом.

## 4. Практический вывод
Для собственного инструмента нужно строить не «копию модели Reve», а проверяемый слой управления изображением:
1. локальная композиционная модель данных;
2. редактор регионов и prompts;
3. адаптер API с явной версией и сериализацией;
4. очередь запросов и состояния `queued/running/succeeded/failed/blocked/unknown`;
5. сохранение request ID, версии, затрат и причин отказа;
6. валидация ответа и явное представление content violation;
7. экспорт проекта в переносимый JSON;
8. локальная история операций без отправки лишних данных.

## 5. Безопасность
- API token хранить на серверной стороне или в защищённом локальном хранилище; не зашивать секрет в статический HTML, репозиторий, source map или клиентский bundle.
- Для публичного приложения использовать backend proxy с лимитами, аутентификацией, ограничением размера тела, таймаутами и защитой от повторной отправки.
- Не отправлять приватные изображения без явного действия пользователя.
- Ограничивать размер входных изображений и JSON layout; проверять MIME и реальный формат файла.
- Логировать метаданные с минимизацией персональных данных; не сохранять токены и полные prompts по умолчанию.
- Учитывать, что browser SDK — транспортная обёртка, а не механизм защиты секрета.
