# Техническое задание: локальная композиционная студия с адаптером Reve

## 1. Цель
Создать инструмент, где человек вручную задаёт структуру изображения (регионы, расположение, текстовые инструкции), видит её до отправки, контролирует отправляемые данные и получает воспроизводимый журнал запросов. Система не должна маскировать неизвестные возможности API и не должна требовать облачного аккаунта для локального редактирования композиции.

## 2. Слои архитектуры

### A. Domain model (локально, без сети)
`Project { schemaVersion, title, canvas:{width,height,aspectRatio}, regions:[Region] }`
`Region { id, label, prompt, bbox:{x,y,width,height}, zIndex?, locked?, metadata? }`
Все bbox в локальной модели нормализованы в диапазон 0..1. При сериализации в API-формат нужен отдельный адаптер с проверкой фактической схемы целевой версии SDK. Не смешивать внутреннюю модель редактора с wire-format API.

### B. UI / editor
- Canvas с регионами и доступным списком регионов.
- Добавить, выбрать, переместить, изменить размер, удалить.
- Редактировать label и prompt в панели свойств.
- Блокировка региона и управление порядком — после MVP.
- Undo/redo и клавиатурное управление — следующая итерация.
- Контраст, крупные интерактивные зоны, видимый фокус, подписи элементов; не полагаться только на цвет.
- Уважать `prefers-reduced-motion`; вся работа с регионом должна иметь альтернативу drag-and-drop через числовые поля.

### C. Project storage
- MVP: импорт/экспорт JSON и ручное сохранение файла.
- Следующая версия: IndexedDB, локальная история версий и восстановление последнего проекта.
- Не отправлять локальный проект на сервер до явного действия пользователя.

### D. Reve adapter (отдельный модуль, не включён в HTML-прототип)
- Закрепить версию пакета/endpoint и записывать её в журнал.
- Типизированные функции: `createLayout`, `extractLayout`, `renderLayout`, `reconcileLayout`; наличие/имена подтвердить по конкретной установленной версии SDK.
- Слой преобразования `Project ↔ SDK Layout`; неизвестные поля сохранять только если API-контракт это разрешает.
- Валидировать bbox, обязательные поля, размеры входных файлов и количество регионов.
- Ответ нормализовать в `RequestResult`: `status`, `requestId`, `version`, `creditsUsed`, `creditsRemaining`, `image`, `contentViolation`, `errorCode`, `retryable`.
- Различать HTTP failure, timeout, content violation, invalid payload, quota/credits error и unknown response.
- Не делать автоматический retry на неидемпотентный запрос без политики дедупликации.

### E. Server proxy для публичного веб-приложения
- Секреты только на сервере; не включать API token в клиентский bundle.
- Rate limiting по пользователю/сессии, лимит размера, таймаут, allowlist endpoint.
- Идемпотентный ключ, где поддерживается; request ID сохранять.
- Секреты исключить из логов и ошибок.
- CORS и CSRF-модель определить по архитектуре приложения.

## 3. Контракт локального JSON
См. `04_LAYOUT_EXAMPLE.json`. Это контракт приложения, а не гарантия точного формата Reve. До реальной интеграции требуется адаптер, основанный на pinned версии SDK и тестовом API-ответе.

## 4. Нефункциональные требования
- Редактирование не требует сети и API token.
- Никаких внешних запросов из автономного HTML.
- Все ошибки сообщают, что именно не удалось и можно ли продолжить локально.
- Импорт JSON не должен выполнять код; использовать `JSON.parse`, структурную валидацию и лимит размера.
- Не использовать `innerHTML` для вставки пользовательских label/prompt.
- Не считать наличие HTTP 200 доказательством успешной генерации: проверить тело ответа и content-violation поле.
- Все параметры должны иметь текстовые альтернативы для assistive technology.

## 5. План реализации
1. Зафиксировать SDK/package/API version и сохранить lockfile.
2. Получить безопасный тестовый токен и сверить реальные сигнатуры, типы и ответы.
3. Добавить JSON Schema или эквивалентный валидатор для локального Project.
4. Написать unit tests для bbox/импорта/экспорта и адаптера.
5. Реализовать серверный proxy, если клиент публичный.
6. Реализовать очередь, таймауты и состояния запросов.
7. Добавить integration tests на тестовых изображениях; проверять content violation и отказ API.
8. Провести доступностный аудит клавиатуры и screen reader.
9. Выпустить с логом версии, SHA256 артефактов и списком известных ограничений.

## 6. Definition of Done
- 100% unit tests для валидатора, сериализации и состояний проходят.
- Импорт malformed JSON безопасно отклоняется.
- Невалидный bbox не отправляется в API.
- Секрет не обнаруживается в HTML/JS bundle/source maps и клиентских логах.
- Timeout, 4xx, 5xx, content violation и неизвестное тело ответа отображаются раздельно.
- Проект можно редактировать, экспортировать и открыть повторно без сети.
- Проверена работа без мыши для ключевых действий.
- Все заявления о production readiness подкреплены фактическими логами тестов.

## 7. Риски и решения
- **API schema drift:** pinned version + contract tests.
- **утечка токена:** server-side proxy, secret scanning.
- **несовпадение локального и API Layout:** отдельный adapter и round-trip tests.
- **стоимость повторных запросов:** явное подтверждение запуска, лимиты, idempotency.
- **непредсказуемый генеративный результат:** показывать промпт и layout до отправки; не обещать точную геометрию/детерминизм.
- **недоступный drag-and-drop:** числовые поля и кнопки перемещения/изменения размера.
