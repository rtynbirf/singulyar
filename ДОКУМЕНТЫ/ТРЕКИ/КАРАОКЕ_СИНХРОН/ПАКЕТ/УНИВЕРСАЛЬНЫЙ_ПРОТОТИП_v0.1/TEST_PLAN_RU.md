# План тестирования и доказательств

## 1. Принцип

Отделять заявления от доказательств. Для каждой функции записывать: `CLAIM → CODE → OFFICIAL SPEC → TEST → VERDICT`. Не объявлять тест успешным, пока он не был выполнен в целевой среде.

## 2. Дымовые проверки
1. `npm install` завершается без ошибок.
2. `npm run check` проходит.
3. `npm start` запускает сервер на порту 8080.
4. `http://localhost:8080` отдаёт интерфейс.
5. В двух окнах можно создать комнату и присоединиться по коду.
6. Третий клиент получает отказ.
7. Микрофон запрашивает разрешение и показывает понятную ошибку при отказе.
8. Два клиента обмениваются аудио в сети, где WebRTC соединение возможно.
9. Два клиента обмениваются текстом.
10. TTS озвучивает текст при доступном системном голосе.
11. Остановка микрофона останавливает отправку исходного аудио.
12. Закрытие вкладки показывает выход у партнёра.

## 3. Сетевые тесты
- Оба клиента в одной Wi-Fi сети.
- Разные сети.
- Один клиент через мобильную сеть.
- Плохой Wi-Fi, высокий RTT и джиттер.
- Смена Wi-Fi ↔ мобильная сеть.
- Блокировка UDP и сценарий, требующий TURN.
- Перезапуск сигналинг-сервера во время сеанса.

## 4. Функциональные тесты
- Язык источника и язык получателя разные.
- Пустое сообщение не отправляется.
- Сообщение длиннее лимита отклоняется сервером.
- Некорректный JSON не ломает процесс.
- Неизвестная фраза не подменяется выдуманным переводом.
- Синтез речи останавливается по кнопке.
- Комната исчезает из памяти после ухода обоих участников.

## 5. Доступность
- Полное управление клавиатурой.
- Видимый фокус.
- Проверка масштаба 200%.
- Проверка ширины 320 px.
- Screen reader озвучивает статусы.
- Цвет не является единственным способом сообщить состояние.
- Кнопки имеют понятные имена.
- Ошибки объясняют следующий шаг.

## 6. Будущий переводчик: измерения
Для каждой языковой пары и типа контента отдельно измерять:
- WER/CER для распознавания, с оговоркой о несовершенстве этих метрик для пения;
- оценку смысла перевода носителями языка;
- точность тайминга слов и слогов;
- долю строк, пригодных к пению на заданной мелодии;
- задержку p50/p95 от конца фразы до результата и от начала фразы до первого полезного результата;
- артефакты вокала и узнаваемость говорящего в слепом тесте;
- долю случаев, когда система корректно отказывается от низкоуверенного результата;
- расход батареи, CPU/RAM и сетевой трафик.

## 7. Матрица покрытия
Минимально: 2 языка × 3 жанра × 3 условия записи (чисто, шум, эхо) × 2 устройства × 2 сети. Не объединять результаты всех ячеек в одну среднюю цифру, скрывающую слабые сочетания.

## 8. Формат записи дефекта
- ID;
- версия приложения/модели;
- устройство/браузер/ОС;
- языковая пара;
- входной материал и права на него;
- шаги воспроизведения;
- ожидаемый результат;
- фактический результат;
- метрика/лог без избыточных персональных данных;
- severity;
- решение и регрессионный тест.

## 9. Вердикты
- `PASS`: критерий выполнен на указанной матрице.
- `FAIL`: критерий не выполнен.
- `BLOCKED`: тест не проведён из-за внешнего ограничения.
- `UNKNOWN`: доказательств недостаточно.
