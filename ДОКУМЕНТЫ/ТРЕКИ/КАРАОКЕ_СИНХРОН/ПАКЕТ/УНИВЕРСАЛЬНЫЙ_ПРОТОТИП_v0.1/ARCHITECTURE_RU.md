# Архитектура прототипа

## 1. Цель

Проверить пользовательский сценарий «два человека в разных странах — разные языки — один сеанс совместного исполнения» без ложного утверждения, что перевод певческого голоса уже решён.

## 2. Компоненты

1. **Web UI (`index.html`)** — настройки языка, комнаты, микрофона, текста, демонстрационной озвучки и караоке-строки.
2. **Сигналинг (`src/server.js`)** — HTTP для статики и WebSocket для согласования WebRTC и пересылки небольших текстовых сообщений.
3. **WebRTC** — прямая передача аудиопотока между браузерами. Сигналинг не передаёт сам аудиопоток.
4. **Speech Synthesis** — системный синтезатор браузера, если он поддерживает выбранный язык и голос.
5. **Демонстрационный словарь** — фиксированные примеры, не модель машинного перевода.
6. **Будущие адаптеры** — ASR, перевод, singing alignment, singing voice conversion, генерация аудио.

## 3. Поток текущей версии

### Подключение
- Участник создаёт код комнаты или вводит существующий.
- Клиент подключается к `/signal` через WebSocket.
- Сервер ограничивает комнату двумя участниками.
- Стороны обмениваются offer/answer и ICE-кандидатами.
- WebRTC устанавливает аудиоканал, когда сеть и NAT позволяют прямое соединение.

### Голос
- Браузер запрашивает микрофон через `getUserMedia`.
- Аудиодорожка добавляется в `RTCPeerConnection`.
- Удалённая дорожка воспроизводится в `<audio>`.
- В текущей версии звук не переводится и не преобразуется.

### Текст
- Исходный текст может быть передан партнёру.
- Демонстрационный словарь подставляет заранее заданный результат для нескольких известных фраз.
- Синтез речи озвучивает текст на выбранном языке, если браузер располагает подходящим голосом.

## 4. Целевая архитектура переводчика

```text
Микрофон / музыкальный микс
        |
        v
  Audio capture + timestamps
        |
        +--> Voice / source separation (optional)
        |
        v
  Singing ASR + confidence
        |
        v
  Text / phoneme / note alignment
        |
        v
  Translation candidates
        |
        v
  Syllable + prosody + note fitting
        |
        v
  Singing voice conversion / synthesis
        |
        v
  Quality gate + provenance labels
        |
        v
  Remote playback + karaoke captions
```

Каждый модуль должен иметь интерфейс, версию, языковую пару, входной и выходной формат, тайм-аут, оценку уверенности и диагностические метрики. Неуверенный результат нельзя маркировать как достоверный.

## 5. Ключевое архитектурное решение

Не пытаться в первой версии одним непрозрачным вызовом решить «распознать песню, перевести, сохранить голос, ноты и эмоции». Сначала получить измеримые отдельные результаты для:
- распознавания текста спетого вокала;
- перевода смысла;
- пригодности перевода к пению;
- сохранения мелодии и голоса;
- задержки и устойчивости.

## 6. Данные и временные метки

Минимальный объект аудиособытия:
- `sessionId`: случайный идентификатор сеанса;
- `participantId`: псевдоним участника;
- `sequence`: номер фрагмента;
- `captureTime`: монотонная временная метка;
- `sourceLanguage`: BCP-47;
- `mediaKind`: `original-audio`, `translated-audio`, `text`, `karaoke-cue`;
- `confidence`: число или `null`;
- `modelId` / `modelVersion`: для машинного результата;
- `retention`: правило хранения.

Не включать в диагностические события содержание песни или голосовые данные без отдельного согласия.

## 7. Ограничения текущего сервера

- Временные комнаты хранятся в памяти процесса.
- Максимум два участника.
- Нет постоянных аккаунтов, очередей, базы данных, rate limiting и TURN.
- Комнаты не защищены паролем; короткий код — не достаточная авторизация для чувствительных разговоров.
- Нет TLS в локальном режиме.
- Перед публичным запуском нужен внешний reverse proxy с HTTPS/WSS, TURN, лимиты и модель авторизации.
