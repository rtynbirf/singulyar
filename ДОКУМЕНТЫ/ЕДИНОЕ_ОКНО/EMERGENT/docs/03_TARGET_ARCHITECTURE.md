# 03 — Целевая архитектура

## Слои

1. **Human interface** — единая точка начала; режимы простоты/полноты, доступные способы ввода/вывода, объяснение рекомендаций.
2. **Intent & Relationship model** — человек, отношения, круг, цель, аудитория, срочность, согласие, контекст. Идентичность не обязана равняться аккаунту одного провайдера.
3. **КРИСТАЛЛ / semantic event core** — версионируемые события и типизированные сущности. Не заменяет существующие страницы и модули; связывает их общим контрактом.
4. **ОРКЕСТРАТОР** — собирает возможности адаптеров, проверяет ограничения, показывает выбор, управляет retry и статусом. Не отправляет без consent.
5. **ФАБРИКА / composition engine** — подбирает цепочку преобразований: например, текст → озвучивание, аудио → транскрипт → текст. Каждая трансформация имеет provenance и возможность отмены, где это возможно.
6. **Adapters** — телефон/SMS, Matrix, ActivityPub, email, файл/медиа, системный TTS/STT, AAC, календарь, кошелёк-переход. Каждый адаптер отдельный и явно маркирует уровень готовности.
7. **Transport & sync** — local queue, optional server, federation, WebRTC signalling. Разные гарантии доставки не маскируются одним флагом.
8. **Memory & audit** — локальная память и журнал по решению человека; сроки хранения и удаление прозрачны.

## Модули Singulyar — карта ответственности (публично подтверждённые точки + проверка локальной интеграции)

- `·15 ОРКЕСТРАТОР`: запуск сценария и согласование адаптеров.
- `·17 ЗАЛ`: пространство взаимодействия/комната, только если его фактический контракт подтверждён.
- `·18 СОБЫТИЕ`: семантические события, таймлайн и жизненный цикл действия.
- `·19 ЧЕЛОВЕК`: профиль возможностей и предпочтений, без вывода чувствительных признаков автоматически.
- `·20 ФОНЕТИКА`: текст/фонетика/речь и преобразования, не владелец всего messaging.
- `·21 ОБЩЕНИЕ`: разговор и составные сценарии общения.
- `·22 СВЯЗЬ`: транспорт, доступность каналов и delivery state.
- `·23 КРУГ`: отношения, участники, аудитории и разрешения.
- `·24 ПОЧТА`: email-адаптер/почтовые сценарии.
- `·25 КОШЕЛЁК`: денежные намерения и переход к реальному провайдеру; реальные операции отдельны.
- `·26 ЛИНИЯ`: долгоживущие каналы/контакты/линия связи после проверки текущего смысла модуля.
- `·29 СВОБОДА`: существующий UI над Composition Engine — использовать как архитектурную опору для выбора из примитивов, не дублировать.
- `·30 ТКАНЬ`: существующий P2P Human Information Fabric — исследовать его семь ES-модулей перед добавлением транспорта.
- `·41 НАМЕРЕНИЕ`: уже присутствует в hub; новый composer должен подсоединяться к существующему потоку намерения.
- `·53 СВЯЗЬ ЧЕЛОВЕКА`: существующая дверь связи человека — проверить контракт и назначение в pinned checkout.
- `·54 ПИР`: существующая дверь живой связи WebRTC P2P; сигнализация/relay и реальные гарантии проверяются отдельно.
- `КРИСТАЛЛ`: общий протокол событий; `·02 ФАБРИКА`: композиция; `ПАМЯТЬ`: управляемая память. Не создаём вторую дверь `·43`: она уже учтена в текущем доме.

## Поток

`User intent → consent gate → capability discovery → explainable proposals → human choice → optional transformation chain → adapter preflight → send confirmation → delivery state → audit event → optional memory`.

## Статусы доставки

`draft → approved → queued → sending → sent-to-provider → delivered (only if recipient receipt is supported) / failed / unknown`. Нельзя подменять `sent-to-provider` статусом `delivered`. Для каналов без read receipt это прямо отображается.

## Конкуренция и офлайн

Для локальных черновиков достаточно локального ID и временной метки. Для межустройственной синхронизации понадобятся event IDs, idempotency, causal metadata, конфликтная политика, подписи и проверяемые права. Append-only журнал сам по себе не решает конфликты и не доказывает истинность событий.
