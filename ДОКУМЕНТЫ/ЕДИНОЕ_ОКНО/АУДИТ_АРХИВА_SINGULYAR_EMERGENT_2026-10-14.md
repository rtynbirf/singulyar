# Независимый технический аудит архива Singulyar Emergent

**Объект:** `SINGULYAR_EMERGENT_ПРОТОТИП_ТЗ_ДОРОЖНАЯ_КАРТА_ДОКУМЕНТАЦИЯ.zip`  
**Дата проверки:** 2026-10-14  
**Метод:** проверка структуры ZIP, чтение исходников и документации, `node --check` для JavaScript, запуск имеющегося набора тестов, статическое сопоставление UI-event с JSON Schema.  
**Итог:** архив содержит запускаемый демонстрационный UI и несколько небольших функций ядра, но не содержит работающей коммуникационной системы. Обнаружены критические разрывы между UI, ядром, схемой события и адаптерами. Успешные 10/10 тестов не проверяют UI и не обнаруживают эти разрывы.

## Краткий вердикт

- ZIP целостен: `zipfile.testzip()` не обнаружил повреждений; 38 записей, включая каталог.
- `node --check` прошёл для проверенных JS-файлов.
- `node tests/core.test.js`: 10/10 PASS.
- **Это не означает, что продукт работает:** тестируется только `src/core.js`; браузерный UI, JSON Schema, адаптерный реестр и интеграционный мост в тесты не включены.
- Интеграционный код не подключён к опубликованному сайту. Внешние каналы не работают.

## P0 — блокирующие ошибки контракта/данных

### P0.1. JSON, который экспортирует UI, не соответствует объявленной JSON Schema

**Файлы:** `prototype/app.js:30`, `schemas/communication-intent.schema.json:4-12`.

UI формирует поля `eventId`, `createdAt`, `actor`, `proposal`, `privacy`, но схема запрещает неизвестные свойства через `additionalProperties: false`. При этом UI не выдаёт обязательное поле `consentToSend`. Дополнительно UI выставляет `provenance.status = "user-authored-draft"`, тогда как схема разрешает только `draft`, `approved`, `sent`, `failed`, `unknown`.

**Следствие:** экспортированный JSON невалиден по собственному контракту. Нет теста, который проверяет сериализованный объект против схемы.

**Исправление:** выбрать один канонический event envelope, согласовать схему и код, добавить настоящий JSON Schema validator в тесты и проверить экспорт UI этим валидатором.

### P0.2. Значения модальностей UI несовместимы с ядром и схемой

**Файлы:** `prototype/index.html:1` (селекторы `from`/`to`), `prototype/app.js:30`, `src/core.js:3, 8-16`, `schemas/communication-intent.schema.json:8-10`.

Селекторы используют видимые русские подписи как значения (`Текст`, `Речь / диктовка`, `Брайль / тактильный вывод` и т. п.). Ядро и схема ожидают машинные enum-значения: `text`, `speech`, `braille`, `tactile`, `aac` и т. д. UI экспортирует подписи напрямую.

**Следствие:** UI-event не может пройти валидацию и не может безопасно использоваться адаптерами.

**Исправление:** у каждого `<option>` задать стабильный `value` из общей схемы, а отображаемый текст оставить локализованным; покрыть все значения тестами.

### P0.3. UI, core, schema и adapter registry — четыре не связанные части

**Файлы:** `prototype/app.js`, `src/core.js`, `src/adapters.js`, `schemas/communication-intent.schema.json`.

`prototype/app.js` не импортирует и не вызывает `src/core.js`, не использует `src/adapters.js` и не валидирует данные по схеме. Рекомендации задаются вручную в таблице `choices`. Поэтому успешные тесты core не подтверждают поведение интерфейса.

**Следствие:** исправление ядра не меняет работу интерфейса; реестр возможностей не влияет на рекомендации; контракты не защищают реальные данные.

**Исправление:** выделить общий модуль модели/валидации, подключить его к UI и адаптерам, а рекомендации вычислять по реальным capability manifests.

## P1 — основные функциональные декларации, не подтверждённые кодом

### P1.1. Рекомендации не учитывают выбранные модальности, адресата, срочность или возможности устройств

**Файл:** `prototype/app.js:18-29`.

`from`, `to`, `recipient` и `urgency` читаются для журнала, но набор рекомендаций выбирается только по `intent`: `choices[intent]`. Нет модели отношений, профиля предпочтений адресата, доступности канала, стоимости, приватности, сетевого состояния или совместимости устройств.

**Следствие:** текст интерфейса обещает адаптацию к человеку, но на деле выдаёт статические варианты. Это не композиционный движок и не эмерджентное ранжирование.

**Исправление:** реализовать функцию scoring с объяснимыми факторами и hard constraints; если данных нет — явно показывать «неизвестно» и спрашивать пользователя, а не угадывать.

### P1.2. Выбранный вариант сохраняется как устаревший снимок

**Файл:** `prototype/app.js:29-32`.

При нажатии «Выбрать для черновика» вызывается `lastEvent = makeEvent(...)`. Если затем пользователь меняет текст, адресата, намерение, срочность или модальности, `Сохранить черновик` и `Экспортировать событие JSON` используют старый `lastEvent` (`lastEvent || makeEvent()`) и теряют изменения.

**Воспроизведение:** сформировать варианты → выбрать один → изменить текст или адресата → сохранить/экспортировать → в JSON остаётся прежний снимок.

**Исправление:** хранить выбранный `choice` отдельно; собирать event из текущего состояния в момент сохранения/экспорта.

### P1.3. Поиск по локальным записям не реализован как поиск

**Файлы:** `prototype/app.js:26, 36`; `prototype/index.html` — подпись поля поиска.

Для намерения `find` показывается обещание «Поиск по локальным записям», но код не строит индекс людей, сообщений, файлов или истории. Поле поиска фильтрует только 13 категорий; сохранённый JSON лишь проверяется на подстроку, а найденная запись не показывается и не открывается.

**Следствие:** пользовательский сценарий «найти человека, сообщение или материал» не реализован, несмотря на присутствие в интерфейсе.

**Исправление:** либо честно переименовать сценарий в «поиск по каталогу», либо реализовать локальный индекс с результатами, типами объектов, происхождением и управлением приватностью.

### P1.4. Восстановление черновика не работает

**Файл:** `prototype/app.js:34`.

При старте код обнаруживает ключ в `localStorage` и меняет статус на «Найден локальный черновик», но не читает JSON обратно в поля формы и не восстанавливает выбранный вариант.

**Следствие:** сохранение есть, пользовательское восстановление — нет.

**Исправление:** валидировать загруженный объект, показать предварительный просмотр и восстановить поля; обработать повреждённый/устаревший JSON и возможность отказа от восстановления.

### P1.5. «Очистить черновик» очищает не весь черновик

**Файл:** `prototype/app.js:32`.

Очищаются `localStorage`, текст и адресат; остальные поля формы, результаты вариантов и журнал остаются на экране. Пользователь может принять остатки состояния за полностью очищенную сессию.

**Исправление:** определить точную семантику «очистить», сбрасывать всё состояние и UI, либо назвать действие «Удалить сохранённый черновик и текст».

### P1.6. Ни один адаптер не реализует внешнюю доставку

**Файл:** `src/adapters.js:1-9`.

Matrix, ActivityPub и платёжный переход — декларации со статусом `not-connected` и `enabled:false`. `system-tts` имеет статус `capability-check-required`, но фактического вызова TTS нет. `local-draft` — описание, а не сетевой адаптер. Нет интерфейса `send`, auth, retry, timeout, idempotency, receipts, отмены или реальных delivery events.

**Следствие:** это реестр-план, не работающие интеграции. Это нормально для архитектурного эскиза, но нельзя считать интеграции реализованными.

### P1.7. `canDeliver()` не является полноценным безопасным шлюзом отправки

**Файл:** `src/core.js:16`.

Проверяются только `consentToSend`, `adapter.status === 'connected'` и `adapter.enabled === true`. Не проверяются поддержка конкретного intent/модальностей, получатель, содержимое, конкретный текст согласия, срок действия подтверждения, повтор события, идемпотентность и состояние платежа. Функция сама ничего не отправляет.

**Исправление:** переименовать её в проверку минимальных условий либо реализовать контракт preflight с capability validation, target binding, одноразовым подтверждением конкретного действия и защитой от повторов.

### P1.8. `createIntent()` валидирует не весь контракт

**Файл:** `src/core.js:5-15`.

Проверяются `urgency` и модальности, но не enum `intent`, типы `text`/`recipient`/`source`, длины, неизвестные поля или структуру входа. Значение `intent:'anything'` принимается ядром, хотя схема его запрещает.

**Исправление:** полная runtime-валидация по общей схеме, ограничения размеров и отказ при неверных типах/неизвестных значениях.

### P1.9. Интеграционный bridge — не интеграция с семантическим движком

**Файл:** `integrations/intent-composition-panel.js:30-67`.

Код использует набор regex по тексту и подставляет ссылки на страницы. Он не вызывает существующий `SNG.намерение`, не читает capability manifests, не получает статус/результаты адаптеров и не проверяет существование ссылок. Регистрация только по факту submit; feature flag в коде отсутствует, хотя в ТЗ он упомянут. `setTimeout(addPanel, 0)` — хрупкий способ угадать момент после текущего обработчика.

**Следствие:** это экспериментальная панель keyword routing, не мост к `·29 СВОБОДА` / `·30 ТКАНЬ` и не единый orchestration layer.

**Исправление:** интегрироваться через документированный API существующего маршрутизатора, ввести флаг, проверку ссылок/возможностей и контрактные тесты на закреплённом commit.

### P1.10. Автоматические рекомендации по ключевым словам легко ошибаются

**Файл:** `integrations/intent-composition-panel.js:30-40`.

Regex вроде `/нем/` срабатывает на произвольные слова с этой последовательностью; `/лицо/` трактует любое упоминание лица как звонок; `/связ/` направляет на P2P даже при другом смысле. Нет оценки уверенности, отрицаний, уточняющего вопроса и тестов на ложноположительные случаи.

**Исправление:** минимально — словарь с границами слов, таблица тестовых фраз/контрпримеров и уточнение при неоднозначности; предпочтительно — структурированный intent parser с объяснимыми правилами и пользовательским подтверждением.

## P2 — качество и доказательность

### P2.1. 10/10 тестов не доказывают работоспособность приложения

**Файл:** `tests/core.test.js`; результат `TEST_RESULTS.txt`.

Тесты проверяют базовые свойства двух-трёх функций `src/core.js`. Они не запускают DOM/UI, не валидируют JSON Schema, не проверяют реестр адаптеров, не тестируют экспорт/восстановление/очистку, не проверяют `intent-composition-panel.js`, ссылки, доступность или работу в браузере.

**Исправление:** добавить тесты схемы, тесты UI в настоящем DOM/браузере, contract tests адаптеров, интеграционные тесты на pinned commit и регрессии текущего Singulyar.

### P2.2. «Объяснимый журнал решения» записывает события интерфейса, а не доказательства решения

**Файл:** `prototype/app.js:29-31`.

Журнал отображает значения формы и количество статических вариантов; он не показывает вклад каждого фактора, capability source/version, причины исключения альтернатив или доказанный статус доставки.

**Исправление:** логировать входные факторы, использованные capability claims, причины ранжирования/отказа и provenance с версией; отдельно помечать наблюдаемое и вычисленное.

### P2.3. Исследование практик — ориентир, не глубокий сравнительный обзор рынка

**Файлы:** `docs/01_RESEARCH_AND_BEST_PRACTICES.md`, `docs/11_SOURCE_REGISTER.md`.

Есть полезные ссылки на MDN, WAI-ARIA, Matrix, ActivityPub и JSON Schema. Но отсутствуют систематическая сравнительная матрица, критерии отбора, проверенные версии, датированные результаты совместимости, анализ конкурирующих архитектур и протокол воспроизводимости. Сам документ корректно признаёт, что обзор не исчерпывающий.

**Следствие:** формулировка «изучены лучшие мировые практики» была бы чрезмерной; точнее — «составлен начальный обзор нескольких официальных стандартов».

### P2.4. Архитектурные документы существенно опережают реализацию

**Файлы:** `docs/03_TARGET_ARCHITECTURE.md`, `docs/04_SECURITY_PRIVACY.md`, `docs/06_ROADMAP.md`, `docs/07_IMPLEMENTATION_TZ.md`.

Документы обсуждают event lifecycle, provenance, федерацию, E2EE, offline sync, конфликтную политику, SBOM, rollback и threat model, но большая часть этого не реализована. ТЗ требует PR в исходном репозитории, pinned commit, regression suite и browser checks — эти работы в архиве не выполнены.

**Следствие:** пакет в значительной мере является проектной спецификацией, а не завершённым инженерным продуктом.

### P2.5. Заявления о локальном сохранении нуждаются в обработке отказов

**Файл:** `prototype/app.js:32, 34, 36`.

Чтение хранилища частично обёрнуто в `try/catch`, но запись в `localStorage` при сохранении не обёрнута. При quota/security exception обработчик может оборваться без понятного пользователю результата. Поиск локального черновика сравнивает сериализованный JSON как строку, а не ищет по определённым полям.

**Исправление:** единый storage adapter с обработкой quota/denied, подтверждением успешной записи и экспортируемым журналом ошибок без утечки содержимого.

### P2.6. Браузерная проверка прототипа не была подтверждена этим аудитом

JS syntax checks и unit tests прошли. Автоматический Chromium dump в среде аудита завис/превысил лимит времени; поэтому в рамках этого аудита нельзя заявлять о полноценном end-to-end browser pass. Это отдельная неопределённость, не доказательство неисправности браузера или страницы.

## Что действительно реализовано

1. Статическая HTML/CSS/JS-демонстрация выбора намерения.
2. Каталог из 13 классов коммуникации.
3. Статические наборы вариантов по восьми значениям намерения.
4. Локальная запись одного черновика через `localStorage` (с оговорками выше).
5. Выгрузка JSON (но JSON не соответствует объявленной схеме).
6. Чистые функции `createIntent`, `rankAdapters`, `canDeliver` с ограниченной валидацией/ранжированием.
7. Десять базовых unit-тестов этих функций.
8. Экспериментальный скрипт, добавляющий ссылки по regex в существующую форму, но не подключённый к production.

## Что не реализовано

- Реальная доставка сообщений по любому внешнему каналу.
- Интеграция Matrix, ActivityPub, email, SMS/телефонии, WebRTC, push или платёжного провайдера.
- Работающий адаптерный API и capability discovery.
- Реальный алгоритм рекомендаций, учитывающий модальности/предпочтения/отношения/сеть/приватность.
- Поиск по людям, сообщениям, контактам и файлам.
- Синхронизация между устройствами, очереди, retry, idempotency и delivery receipts.
- Проверенная безопасность/E2EE.
- Подтверждённое соответствие WCAG 2.2 AA и пользовательские тесты.
- Изменения в GitHub-репозитории и интеграция в live-сайт.

## Приоритет исправлений

1. Согласовать schema ↔ core ↔ UI; добавить валидацию каждого экспортируемого события.
2. Перестать сохранять устаревший `lastEvent`; реализовать корректное восстановление и очистку.
3. Подключить UI к общему ядру и capability manifests; убрать статическую имитацию рекомендаций или честно назвать её демонстрацией.
4. Определить минимальный реальный end-to-end сценарий с одним действующим адаптером и измеримым подтверждением результата.
5. Добавить браузерные тесты и regression gate на точном commit Singulyar.
6. Только после этого развивать Matrix/ActivityPub/телефонию/платежи/синхронизацию и проводить независимый security/accessibility review.

## Финальный вердикт

Архив **не пустой и не полностью фиктивный**: в нём есть настоящий фронтенд-демо, небольшой JS core и тесты. Но центральное обещание — система, которая адаптирует и композирует реальные способы коммуникации, — пока **не реализовано**. Более того, собственный экспорт события не проходит собственную схему, а UI обходит ядро и адаптеры. Это главные технические дефекты, которые нужно исправить до любых заявлений о «рабочем прототипе» в продуктовом смысле.
