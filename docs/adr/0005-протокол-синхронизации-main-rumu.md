# ADR-0005 · Протокол синхронизации main↔rumu до флипа дефолта

- Статус: принято (Волна ×4, 2026-11-09, Task W4-H)
- Контекст: issue #63 (дрейф rumu...main = 631/770, diverged, прогон
  main-drift-watch 42495670584), issue #62 п.1 (T11/П-11), ADR-0004
- Машинная проверка гейтов: `.github/workflows/parity-flip-check.yml` +
  `scripts/parity_flip_report.py` (П52, issue #64)

## Контекст

Репозиторий живёт на двух головах: `rumu` (дефолт, Pages/живой сайт, cron-пломбы)
и `main` (рабочая линия латок). Истории РАЗОШЛИСЬ (diverged 631/770): общий
предок далеко позади, прямые merge/cherry-pick между ветками тянут за собой
чужие состояния и ломают сайт. ADR-0004 зафиксировал статус-кво и три гейта
флипа дефолта. Этот ADR описывает, как работать с дрейфом каждый день до флипа.

## Решение

1. **Целевая ветка по умолчанию — `rumu` до особого решения.** Флип дефолта на
   `main` выполняет ТОЛЬКО Хозяин одной командой
   (`PATCH /repos/rtynbirf/singulyar {"default_branch": "main"}`) и только после
   гейтов (а)(б)(в) из ADR-0004. Агенты флип НИКОГДА не выполняют.
2. **Синхронизация — портированием, не слиянием.** Пока головы diverged:
   - перенос работы main→rumu (или обратно) делается КОПИРОВАНИЕМ содержимого
     отдельными коммитами с пометкой «порт из <ветка>: <суть>»;
   - merge и cherry-pick через разошедшиеся истории ЗАПРЕЩЕНЫ: они тянут
     чужие деревья и ломают Pages;
   - каждая сторона несёт своё: rumu — сайт и живые пломбы, main — рабочие
     латки; дублирование работы фиксируется в журнале, а не прячется.
3. **Машинные гейты флипа** (weekly + ручной запуск, отчёт — комментарием в
   issue #63):
   - (а) parity контента Pages: `git diff --name-only origin/rumu origin/main`
     и обратно; флип разрешён, когда site-файлов в расхождении 0 (служебные
     пути репо — `.github/`, `docs/`, `harness/`, `reports/`, `server/`,
     `scripts/`, `ИНСТРУМЕНТЫ/`, `*.md` — в гейт (а) не входят, но показываются
     в отчёте отдельной строкой);
   - (б) зелёный такт-гейт на main: последний прогон workflow `такт_гейт.yml`
     на ветке main имеет conclusion=success;
   - (в) слово Хозяина: label `owner-approved` на issue #63 — единственный
     не-машинный триггер, поле в отчёте.
4. **Ежедневный надзор** остаётся на `main-drift-watch.yml` (ADR-0004): он
   открывает issue-сводку при изменении дрейфа; настоящий протокол не заменяет
   его, а достраивает до проверки готовности флипа.

## Последствия

- Плюс: дрейф измерим и отчуждаем (отчёт в #63 по факту, не по вере); флип
  становится решением по факту; histories не перемешиваются.
- Минус: до флипа часть работы живёт в двух экземплярах; отчёт повторяется
  еженедельно (cadence: cron раз в неделю + workflow_dispatch).
- Отмена: после флипа дефолта этот протокол retiring: ветка rumu архивируется
  тегом, синхронизация вырождается в обычную работу на main.
